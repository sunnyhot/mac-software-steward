# Performance Baseline - 2026-06-16

## Summary

The strongest measured bottleneck is engineering-loop speed: `npm test` passed but took 77.02s, and `npm run build` passed but took 68.22s. The highest product-runtime risk is scan latency, but scan phase timings are blocked until the scanner exposes per-phase measurements.

Recommended first follow-up: add lightweight scan phase timing instrumentation around the existing scanner boundaries, then use that data to choose between bounded concurrent Sparkle checks, `system_profiler` fallback tuning, and local app metadata caching.

## Scan Baseline

No live scan command was available in the project scripts, so scan phase timing is not measured in this pass. The existing model records only total scan milliseconds in `ScanSummary.scanMs`; it does not persist phase durations.

Source-backed scan observations:

- Static analysis: `native/MacSoftwareSteward/Scanner.swift:23` starts the full scan and already launches Applications, Homebrew, and `mas` work concurrently.
- Static analysis: `native/MacSoftwareSteward/Scanner.swift:70` runs `system_profiler SPApplicationsDataType -json` with a 120s timeout. This is the biggest local scan risk when macOS or a large Applications directory makes `system_profiler` slow.
- Static analysis: `native/MacSoftwareSteward/Scanner.swift:120` runs Homebrew version, prefix, formula list, cask list, and outdated commands in a task group, so simple parallelization is already present.
- Static analysis: `native/MacSoftwareSteward/Scanner.swift:192` runs `mas list` and `mas outdated` concurrently.
- Static analysis: `native/MacSoftwareSteward/Scanner.swift:475` parses each app's `Info.plist` for update capability discovery after app normalization.
- Static analysis: `native/MacSoftwareSteward/Scanner.swift:493` enriches regular app updates after classification.
- Static analysis: `native/MacSoftwareSteward/Scanner.swift:501` loops through apps sequentially, and `native/MacSoftwareSteward/Scanner.swift:513` awaits each Sparkle appcast check before moving to the next app.
- Static analysis: `native/MacSoftwareSteward/SparkleAppcastChecker.swift:9` performs Sparkle feed checks through `URLSession.shared.data(from:)`; `native/MacSoftwareSteward/SparkleAppcastChecker.swift:16` has no explicit per-feed request timeout or bounded concurrency policy.

Likely scan risks:

1. Blocked: phase timings are missing, so the relative cost of Applications, Homebrew, `mas`, local metadata parsing, and Sparkle checks is unknown.
2. Static analysis: sequential Sparkle checks can make scan time scale with the number of manual apps that declare feeds.
3. Static analysis: `system_profiler` may dominate cold scans, especially near its 120s timeout.
4. Static analysis: local `Info.plist` parsing happens for every app and should be measured before adding a cache.

## UI Responsiveness Risk

The UI path is centered on `@MainActor StewardModel`, which is appropriate for published SwiftUI state but makes post-scan synchronous work worth watching.

Source-backed UI observations:

- Static analysis: `native/MacSoftwareSteward/StewardModel.swift:74` recomputes `allUpgradeablePackages` and `availableUpdates` from scan and package progress state.
- Static analysis: `native/MacSoftwareSteward/StewardModel.swift:133` starts `scanSoftware`, then applies the final result to published state.
- Static analysis: `native/MacSoftwareSteward/StewardModel.swift:155` assigns the full scan result on the main actor.
- Static analysis: `native/MacSoftwareSteward/StewardModel.swift:157` recomputes derived package collections immediately after scan assignment.
- Static analysis: `native/MacSoftwareSteward/StewardModel.swift:160` creates inbox items from source issues and app update findings after the scan completes.

Likely UI risks:

1. Static analysis: post-scan result application, derived-data recomputation, and inbox publication are all main-actor work.
2. Static analysis: current derived-data recomputation is simple and likely cheap for normal package counts, but should be measured if scan results grow.
3. Blocked: there is no frame-time or main-thread stall measurement in the repo scripts, so UI smoothness cannot be quantified without instrumentation or manual profiling.
