# 修复：自动检测漏报 Homebrew 更新（元数据缓存陈旧）

## 根因（已确认）
自动检测走 `Scanner.scanBrew`，其中 `brew outdated --greedy` 用的是 Homebrew 本地 API 缓存（`~/Library/Caches/Homebrew/api/`）。MS Office 这类 `auto_updates` cask 只能被 `--greedy` 发现，判定靠缓存里的版本字段。9 点那次缓存陈旧 → 扫出 0 → agent 提前退出跳过了升级阶段的 `brew update` → 缓存永远不刷新，形成死循环。

## 修复策略：方案一（扫描前刷新元数据）
在**共享的** `Scanner.scanBrew` 里，正式扫描（version/prefix/list/outdated 的 task group）之前，先跑一次 `brew update` 刷新 API 缓存。因为 `Scanner.swift` 同时编译进 GUI app 和 agent（`build-native.sh:62` 和 `:73`），这一处改动**同时修好两条路径**。

### 为什么放 scanBrew 而不是各放一处
- 单一数据源，GUI 和 agent 行为必然一致（本次 bug 就是两者行为分叉导致的）。
- agent 里原有的升级前 `brew update`（`AgentMain.swift:107-121`）**保留不动** —— 它是升级阶段保险，作用不同，删掉反而减少保护。

## 具体改动

### 1. `native/MacSoftwareSteward/Scanner.swift` — `scanBrew`（核心，约 194-296 行）
在拿到 `brewPath`（第 198 行）之后、构建 `withTaskGroup`（第 216 行）之前，插入刷新步骤：

```swift
// 扫描前刷新 Homebrew 元数据缓存，避免 brew outdated 用到陈旧的 API 缓存
// 导致 auto_updates cask（如 Microsoft Office）漏报。
// 失败不阻断：用旧缓存继续扫描，宁可漏检也不要让整个 Homebrew 扫描失败。
let updateTimeout: TimeInterval = 60
_ = await CommandRunner.run(brewPath, arguments: ["update"], timeout: updateTimeout)
```

要点：
- 用 `CommandRunner.run`（非 streaming），与同函数其它命令风格一致（第 218-234 行都用 `.run`）。
- **故意忽略返回值/失败**：`brew update` 失败（如离线、HTTP2 报错）时，用旧缓存继续后续扫描 —— 与 agent 升级阶段「失败也继续」的策略（`AgentMain.swift:112-121`）保持一致，避免把刷新失败升级成扫描失败。
- 超时 60s（与同函数 `timeout = 30` 的轻量命令相比略宽，因为 `brew update` 要拉 API；但远小于 outdated 的 120s）。
- 放在 task group 之前、串行执行：必须保证 `outdated` 读到的是刷新后的元数据，不能和其它命令并行（并行会 race）。

### 2. `CHANGELOG.md` — 新增版本条目（顶部，模仿 v0.18.10 风格）
```
## v0.18.11 (2026-08-06)
### 修复：定时巡检漏报 Homebrew 更新
- 定时巡检在 `brew outdated` 扫描前先执行 `brew update` 刷新 Homebrew 元数据缓存，
  修复 auto_updates cask（如 Microsoft Office）因本地缓存陈旧而漏报的问题。
- 刷新失败不阻断扫描，沿用既有容错策略。
```

### 3. 不改动
- `AgentMain.swift`：升级前的 `brew update`（107-121 行）保留，作用不同。
- `StewardModel.scanSoftware`：GUI 扫描路径不改，因为 `scanBrew` 改了它就跟着受益。
- `Models.swift` 的 `BrewScan`：不新增字段（避免触发所有 `BrewScan(...)` 调用点和测试的连锁修改）。
- 不新增测试：`scanBrew` 本身无测试、且通过 `CommandRunner` 静态方法直接 shell out，当前框架无可注入缝隙（已有 `checker:` 闭包模式但本次命令注入价值低）。改动范围小且是「新增一次既有命令调用」，与同函数风格一致。

## 验证
1. `scripts/test-native.sh` —— 确认无回归（现有测试不调用 `scanBrew`，预期全绿）。
2. `scripts/build-native.sh` —— 确认 GUI 和 agent 两个 target 都能编译。
3. 运行时手动验证（可选）：编译后跑 agent `MacSoftwareStewardAgent daily-check --auto-upgrade --greedy`，观察日志里 `brew update` 出现在 `[scan]` 之前。

## 风险与权衡
- **每次扫描多花 2-5s**（`brew update` 拉一次 API）。对定时巡检（每天一次）可忽略；对 GUI 手动检测略有感知，但换来正确性，值得。
- 离线时 `brew update` 会失败/超时 60s 才放行 —— 已通过「失败不阻断」缓解，最坏情况退化为旧行为（用旧缓存扫），不会更糟。
